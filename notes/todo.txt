## Which rules run on Python — MEASURED, not read off the source

Taken 08-04, once the Python parser pack existed (entl PR #13). Every line
below is a rule that was RUN against Python rather than one whose `applies_to`
was read. Two corpora: 44 files of CPython's `Lib` (json, asyncio, argparse,
dataclasses) and a file written to contain one trigger for every regex rule.

### Work today, with no further work at all — seven rules

    file-size          applies to everything; 3 findings
    deep-nesting       needs STRUCTURED_CODE, which Python has; 71 findings
    emoji              needs role != Data; fires
    stray-todo         needs comment syntax, which Python has; fires
    no-comments        same; fires (opt-in)
    unknown-barrier    same; applies. No finding was produced for it, so this
                       one is "applies" and not "demonstrated".
    unused-marker      a meta-rule over suppressions; language-agnostic

`stray-todo` already had a Python test before any of this — it knew `#` starts
a comment because `entl-codebase` has carried a Python LanguageProfile all
along. The pack is not what turned these on; nothing was.

### Lit up BY THE PACK, and by nothing else — two rules

    exact-clone        26 findings
    near-clone         11 findings

Verified by running the same 44 files against a parser-paths directory holding
only the rust pack:

    without the python pack   ok — no findings in 44 file(s)
    with it                   37 error(s) across 44 file(s)

They are tree-sitter rules and read the pack's `[tokenization]` lists. That is
what makes the pack's `literal-node-kinds` load-bearing rather than decorative:
`infact-duplication` classifies only LEAF nodes, so declaring Python's `string`
— which is a parent of `string_start`/`string_content`/`string_end` — would
have named a kind that exists and normalized nothing, and near-clone would have
compared string contents as if they were code. Silently.

### Correctly do NOT apply — four rules

    color  inline-font  inline-svg  motion

All four are `RegexRule`s gated on a language FACET (`STYLE_HOST`,
`COMPONENT_HOST`) that Python does not have. A file containing `"#ff8800"`, a
`font-family` string, an inline `<svg>`, and a `transition:` string produced
zero findings, which is right: a hex string in Python is not a CSS colour.

Do not "fix" these. Giving Python a style facet would make every hex string in
every Python file a finding.

### Genuinely Rust-only, and what each would need — four rules

### A gap this turned up: analysis-incomplete cannot see a MISSING pack

`analysis-incomplete` exists to say "fact-backed analysis could not inspect a
source file". Run over 44 Python files with no Python parser pack configured,
it reported nothing, and straitjacket printed

    ok — no findings in 44 file(s)

which reads as a clean repository and is not one. The rule reports
`facts.diagnostics`, and those are PARSE failures; a file with no parser at all
is never selected and so never becomes a diagnostic. The one case that most
needs saying — an entire language went unanalyzed — is the one it cannot say.

With the pack it works exactly as intended, and names the construct:

    gap.py:1:1  [analysis-incomplete]  exact-clones
      line 1: the grammar cannot read `T =`

[ ] Report a configured source file that no enabled analyzer could claim.
    Cheapest shape: have `infact-analysis` emit a diagnostic for a file whose
    language resolves to no pack, rather than dropping it. That keeps the rule
    unchanged and makes the silence impossible.
    Note this is not hypothetical for any language the fleet has not onboarded
    — it was Python's state until today, and it is every other language's now.

## error-discard: the deny list is deliberately narrow

`[errors]` is enabled in all three repos and all three are clean under it. The
default `deny` list is the five forms that LOSE the failure outright:

    let-underscore, ok-discard, err-arm, ok-binding, iterator-drop

Three forms are recognized but NOT denied. That was measured, not assumed —
turning all eight on across the fleet produced 390 findings, and the three
extra forms accounted for essentially all of them:

    panic          233   `.unwrap()` / `.expect(..)`
    unwrap-or      126   `.unwrap_or*`
    cause-erased    30   `.map_err(|_| ..)`

Each was audited and each is defensible as written:

  - `panic` is a DIFFERENT POLICY. The rule exists because a quiet failure
    produces a quieter run; a panic produces a louder one. Denying panics is
    "no panics", which is a reasonable thing to want and is not this.
    The 25 `expect` sites in the fleet all carry documented invariants.
  - `unwrap-or` is unknowable from syntax. `.unwrap_or_default()` reads
    identically on `Option` and `Result`, and the analyzer resolves no types,
    so it reports these as `Certainty::Possible` and `ambiguous = "skip"`
    drops them. Most real sites were `Option`. Turning this on without type
    resolution buys noise, not signal.
  - `cause-erased` was all `TryFromIntError` -> domain error, propagated with
    `?`. The failure still reaches the caller; only the cause is replaced, and
    `TryFromIntError` carries no information to lose.

[ ] Revisit only with a reason
    `ambiguous = "warn"` is the cheap experiment if `unwrap-or` is ever wanted;
    it reports as warnings without failing a build. Real resolution of the
    Option/Result question needs types, which means semantic observations, not
    a bigger deny list.

## What the rule cannot see

`error-discard` reports a discard and how far it could have travelled. Two
things are outside it, by construction:

  - Whether a caught error is HANDLED WELL. A `match` that binds the error and
    logs it is not a finding, however useless the log.
  - Anything the call graph could not resolve. Reach is reported as `unknown`
    rather than `sealed` when no caller resolves, which is honest but means a
    genuinely sealed discard in dynamically-dispatched code reads as unknown.

[ ] No `[[effects.barriers]]` is configured in any repo
    Same shape of gap as the above: the rule ships, nothing exercises it.
    Tracked in infact/notes/todo.txt where the analysis lives.

## Its own policy

Straitjacket runs its full ruleset on itself and is clean over 39 files.
`no-comments` is ON here and OFF in entl and infact — it was brought from 24
findings to zero by hoisting explanations into doc comments and folding test
commentary into assert messages, which is worth knowing before adding code
here: an ordinary `//` inside a function body is a finding.
